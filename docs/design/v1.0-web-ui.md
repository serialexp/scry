# v1.0 — Web UI (own observability frontend) — Design

Status: draft, not yet implemented — scope decided (Phases 0–3 committed; Alerts UI inert, engine deferred)
Owner: Bart
Last updated: 2026-07-12

> This is the **v1.0 "own UI"** milestone named in `README`/`CLAUDE.md`
> as "the next round". It supersedes the Grafana-adapter direction: scry
> grows its own operator frontend instead of speaking Grafana's
> datasource protocols. PromQL stays demoted (D — "own UI removes the
> Grafana-compat driver"); the metrics view queries through scry's own
> wire, not PromQL.
>
> The visual target is a Claude Design mock (`scry - Redesign.dc.html` +
> `scry-source/`) — a **picture to build toward**, not portable code. It
> is authored in Claude's `dc-runtime` template DSL (`sc-for`/`sc-if` +
> a `DCLogic` class of hardcoded mock data); nothing in it compiles into
> our stack. This doc is the contract for turning that picture into the
> real SolidJS app.

## Why this exists

Today scry has **two disconnected frontends**:

1. The **query app** (`desktop/`, SolidJS + Vite, dual-mode Tauri/browser)
   — a single-screen logs/traces query UI served in-browser by
   `scry-webui` (rust-embed bundle) or natively by Tauri. No metrics view,
   no dashboards, no alerts, no fleet view.
2. The **operator status pages** (`crates/server/src/stats.rs`) — hand-rolled
   inline HTML/CSS/JS served by every `scry ingest` / `scry query` daemon on
   `--stats-listen` (default `:4098`), rendering the Valkey-aggregated fleet
   (D-057).

The Claude Design mock unifies these into **one product UI with four views** —
Explore (query), Dashboards, Alerts, Fleet status — in a single dark,
operator-grade design language. This doc is the contract for building that as
the real app.

**Decided (with Bart):**

- **Full v1.0 UI** — all four views, built as the SolidJS app in `desktop/`
  and served to browsers by `scry-webui`. This is purely a webui + desktop
  effort.
- **The daemons' standalone `stats.rs` pages stay untouched.** They remain the
  zero-dependency, self-served operator page on `:4098`. The new Fleet view is
  a *separate* rendering that lives only in the SPA.
- **Fleet data path:** the new UI asks **queryd** for status; queryd forwards
  the data it already pulls from Valkey via `discover_status_blobs`. scry-webui
  stays a dumb byte-pipe. No new Valkey dependency is added to scry-webui, and
  the browser never talks to Valkey.

## Goals

- One unified SolidJS app covering Explore, Dashboards, Alerts, Fleet.
- Match the mock's design language: near-black canvas (`#14120e`), amber
  accent (`#e8a33d`), teal secondary (`#5bb6a8`), IBM Plex Mono for data /
  system-sans for chrome.
- Reuse the existing wire, transport abstraction, store discipline (SolidJS
  stores, **no prop drilling** — Rule #9), and Arrow result readers. Views are
  presentation on top of the current protocol wherever possible.
- Fleet status reachable in-browser without any new browser→Valkey path:
  queryd is the only Valkey talker; the UI talks only to queryd (via the
  webui relay).
- Preserve dual-mode (Tauri native + browser) for the query views.

## Non-goals (v1.0)

- **No change to the daemons' `stats.rs` pages.** They keep serving `:4098`
  independently; this doc does not touch them.
- **No PromQL.** The Metrics view queries through scry's own wire (matchers +
  time range → series), not a PromQL engine. (PromQL stays demoted.)
- **No Grafana datasource adapters.** The own-UI direction replaces them.
- **No new browser→Valkey or browser→object-store path.** All data flows
  through the queryd wire and the webui relay.
- **Alerts *evaluation* is not committed for v1.0** until its scope is decided
  (see Open questions). The Alerts *view* may ship read-only or be deferred.

## App architecture

The app stays in **`desktop/`** (SolidJS + Vite; Vite is esbuild-backed — the
"compiled toolchain" is already in place) and is served three ways, unchanged:

- **browser** → `scry-webui` serves the rust-embed bundle; `HttpTransport`
  POSTs framed bytes to `/api/query`, target chosen by `X-Scry-Target` id.
- **Tauri** → native TCP via `TauriTransport` (`run_query` invoke).
- selection is the existing lazy `isTauri()` dynamic-import in `store.ts`.

### Routing

Introduce **`@solidjs/router`** and convert `App.tsx` from a single screen to a
routed shell:

```
/            → redirect to /explore
/explore     → Explore (Logs/Traces/Metrics)   [existing query app, re-skinned]
/dashboards  → Dashboards
/alerts      → Alerts
/fleet       → Fleet status
```

The top nav (mock's topbar: brand + nav pills + version + avatar) is the router
shell; the target `<select>` (browser mode) moves into the shell. Each route is
a lazy-loaded view so the Explore path stays light.

### State

Keep the centralized-store discipline (Rule #9). The current `store.ts` is the
Explore store; add **per-view stores** (`store/fleet.ts`, `store/dashboards.ts`,
…) rather than one mega-store, each `createStore` + action functions imported
directly by that view's components. Arrow tables stay in signals, never in a
proxied store (existing constraint).

## View 4 — Fleet status (data path)

The one view that needs new **backend** wiring. The browser must not talk to
Valkey; queryd forwards what it already reads.

```
browser (SolidJS Fleet view)
  │  framed FleetStatusRequest  (X-Scry-Target: <queryd id>)
  ▼
scry-webui  POST /api/query   ── dumb byte-pipe, unchanged ──▶ queryd
                                                                 │ discover_status_blobs(valkey)
                                                                 ▼
                                            FleetStatusResponse { blobs: [json…] }
```

### Wire protocol

Add two variants to the query `QueryFrame` union (`proto/query.schema.json`,
regenerate with `scripts/gen-proto.sh` → `generated_query.rs` + the vendored TS
`generated.ts`):

- `FleetStatusRequest` (tag `0x04`) — client→queryd. Empty body (or an optional
  `role` filter later).
- `FleetStatusResponse` (tag `0x22`) — queryd→client. Carries the array of
  opaque status-JSON blobs (the exact `Vec<String>` `discover_status_blobs`
  returns — the same `StatusSnapshot` JSON the `stats.rs` page renders), plus
  `source` (`valkey`|`local`) and `self_id`.

Modeling it as a **new frame on the existing query wire** (not a new port, not
a new HTTP endpoint) means scry-webui's relay and the browser transport need
**zero** changes — the browser frames a request, the relay pipes bytes, queryd
answers. Only the schema + queryd handler + a TS client function are new.

### queryd handler

queryd already holds a `ValkeyClient` and constructs a `ValkeyFleetSource`
(D-057). To answer the new frame, inject a `FleetSource` into `QueryService`
(mirroring `with_live_discovery` / `with_metrics`) and handle
`FleetStatusRequest` in the connection dispatch: call `blobs()`, reply one
`FleetStatusResponse`. When queryd has **no Valkey**, it **refuses** with a
`StreamError` ("fleet unavailable") — decided, not a `source:local` fallback. A
lone Valkey-less queryd knows nothing about any other instance, so a
single-instance "fleet" would be a misnomer; the UI surfaces the refusal as
"fleet requires Valkey" rather than pretending a one-node fleet. (Mirrors the
D-054 `--live` refuse decision.)

### SolidJS Fleet view

`store/fleet.ts`: a `FleetStatusRequest` sender (reusing `Transport` +
framing), polled every ~1s; parse the JSON blobs into typed snapshots; group
into Ingest/Query sections; badge the `self_id` entry. Rates (bytes/s, records/s)
are computed client-side by diffing successive polls keyed on `instance_id` —
the same technique the `stats.rs` dashboard already uses, and the same
distinct-snapshot diffing the D-057 flicker fix landed (heartbeat republishes
only every ~2s, so diff against the last *distinct* `now_unix_ms`).

## View 2 — Dashboards (Phase 3)

New. A dashboard is a named set of panels; each panel is a saved query (signal +
matchers + viz type) laid out on a grid, with a tree/folder sidebar (per mock).

**Persistence (decided):** the **object store is the source of truth** — each
dashboard is durable JSON under a reserved prefix (e.g. `_dashboards/<id>.json`,
alongside the reserved `_catalog/` prefix; must be skipped by
`reconcile_from_bucket`/`poll_once`/`full_walk` like `_catalog/` is). A
**catalog table** (`dashboards(id, name, folder, updated_at, …)`) is the
runtime-lookup index so listing/searching doesn't walk the bucket — the same
object-store-truth + SQLite-index split the block catalog already uses.
Multi-instance writes converge through the object store (last-writer-wins on
`<id>.json`); the index is rebuilt from the bucket on reconcile. Ship read-only
render first (list + view saved dashboards), then editing. No server-side query
change — panels reuse `QueryRequest`.

## View 3 — Alerts (Phase 4 — inert UI, engine deferred)

The mock shows a rule list, a rule detail (condition + thresholds), and
notification targets. This implies an **alerting subsystem** scry does not have:
rule storage, periodic evaluation against the query engine, a state machine
(ok/pending/firing), and notifier integrations — a backend milestone in its own
right.

**Decided:** the alerting *engine* is **deferred** past v1.0. We ship the Alerts
*view* in the nav so the shape is present, but **inert** — gated behind an
explicit "no backend support yet" empty/locked state (no rule storage, no
evaluation, no live data). This keeps the four-view layout complete without
committing to the engine. When the engine milestone lands, this view wires up to
it; until then it is a deliberate placeholder, not a half-built feature.
